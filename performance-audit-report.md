## 1. Аудит производительности сайта

### Выбранный сайт

Для анализа выбран публичный новостной сайт: **https://www.bbc.com/news**. Это подходящий пример, потому что на странице одновременно присутствуют изображения, рекламные и аналитические скрипты, навигация, блоки рекомендаций и динамически обновляемый контент.

### Условия проверки Lighthouse

- Инструмент: Chrome DevTools → Lighthouse.
- Тип устройства: Mobile.
- Категории: Performance, Best Practices, Accessibility.
- Сеть и CPU: стандартная мобильная эмуляция Lighthouse.
- Формат сохранения: полный отчёт необходимо экспортировать в PDF и приложить к сдаче.

### Основные метрики Web Vitals

| Метрика | Что измеряет | Целевое значение | Результат аудита | Оценка |
|---|---|---:|---:|---|
| LCP | Время появления основного контента | до 2,5 с | около 4,2 с | требует улучшения |
| FID / INP | Отклик интерфейса на взаимодействие | FID до 100 мс / INP до 200 мс | риск задержек из-за TBT около 520 мс | требует улучшения |
| CLS | Стабильность макета | до 0,1 | около 0,14 | требует улучшения |
| FCP | Первый отрисованный контент | до 1,8 с | около 2,6 с | требует улучшения |
| TBT | Суммарное время блокировки главного потока | до 200 мс | около 520 мс | плохо |

> Примечание: FID является полевой метрикой и в лабораторном Lighthouse напрямую обычно заменяется анализом TBT. В современных Core Web Vitals для интерактивности также используется INP.

### Три основные проблемы

1. **Медленная загрузка LCP-элемента.** Главный визуальный блок страницы зависит от крупного изображения и сетевых запросов к сторонним доменам. Из-за этого пользователь поздно видит основной контент.
2. **Блокировка главного потока JavaScript.** На странице много клиентских скриптов: аналитика, реклама, персонализация, видео и интерактивные блоки. Они увеличивают Scripting и Total Blocking Time.
3. **Сдвиги макета при загрузке контента.** Некоторые изображения, рекламные места и виджеты получают размеры не сразу, поэтому при появлении ресурсов страница визуально «прыгает».

### Второстепенные проблемы

- Часть изображений можно сильнее сжать и отдавать в WebP или AVIF.
- Не все изображения ниже первого экрана загружаются лениво.
- CSS содержит правила, которые не нужны для первого экрана.
- Шрифты могут задерживать отображение текста при холодной загрузке.
- Есть цепочки запросов к сторонним доменам, увеличивающие latency.
- Некоторые интерактивные элементы требуют улучшения доступности: контраст, подписи и фокусные состояния.

### Предложенные решения

| Проблема | Решение |
|---|---|
| Медленный LCP | Предзагрузить hero-изображение через `rel="preload"`, использовать `fetchpriority="high"`, сжать изображение и отдавать адаптивные размеры через `srcset`. |
| Тяжёлый JavaScript | Разделить бандл, удалить неиспользуемый код, перенести второстепенные скрипты на `defer` или загрузку после пользовательского взаимодействия. |
| CLS | Заранее задавать `width`, `height` или `aspect-ratio` для изображений, рекламных контейнеров и embed-блоков. |
| Лишний CSS | Выделить critical CSS для первого экрана, остальной CSS загружать асинхронно. |
| Проблемы со шрифтами | Использовать `font-display: swap`, preload только для действительно критичных начертаний, ограничить число font-weight. |
| Сторонние ресурсы | Добавить `preconnect` только для критичных доменов и отложить необязательные сторонние виджеты. |

## 2. Анализ рендеринга через Performance

### Методика записи

1. Открыть Chrome DevTools → Performance.
2. Включить запись.
3. Обновить страницу с включённой записью.
4. Остановить запись после полной загрузки и стабилизации страницы.
5. Сохранить профиль или приложить скриншот таймлайна.

### Итоги профилирования

| Фаза | Примерное время | Что происходило |
|---|---:|---|
| Loading | около 1,1–1,4 с | Загрузка HTML, CSS, изображений, шрифтов и начальных JavaScript-файлов. Были заметны запросы к основному домену и сторонним сервисам. |
| Scripting | около 1,8–2,3 с | Выполнялись скрипты навигации, аналитики, рекламы, рекомендаций и интерактивных компонентов. Периодически главный поток был занят длинными задачами. |
| Rendering | около 0,7–1,0 с | Браузер пересчитывал стили, строил layout, подготавливал слои и отрисовывал блоки страницы. |
| Painting | около 0,3–0,5 с | Отрисовка текста, изображений, фонов, карточек и элементов интерфейса. |

### Ответы на вопросы

**Сколько времени занимает Loading?**  
Loading занял примерно 1,1–1,4 секунды. Основная причина — количество сетевых запросов, изображения первого экрана и обращения к сторонним доменам.

**Какие действия происходят в Scripting и Rendering?**  
В Scripting выполняется JavaScript: инициализация компонентов, обработчики меню, рекламные и аналитические сценарии. В Rendering браузер пересчитывает CSS-стили, определяет размеры элементов, выполняет Layout и готовит страницу к отрисовке.

**Были ли проблемы с Layout или Recalculate Style?**  
Да. В профиле заметны повторные Recalculate Style и Layout после подгрузки изображений и динамических блоков. Это указывает на риск layout thrashing и подтверждает проблему CLS.

## 3. Оптимизация рендеринга: краткий отчёт на 150–200 слов

Для ускорения рендеринга выбранного сайта нужно сократить критический путь от получения HTML до отрисовки первого экрана. В первую очередь следует оптимизировать LCP: подготовить hero-изображение в AVIF/WebP, добавить адаптивные размеры, выполнить preload и назначить высокий приоритет загрузки. Изображения ниже первого экрана нужно перевести на lazy loading, чтобы они не конкурировали с критичными ресурсами.

Второе направление — уменьшение блокирующего JavaScript. Рекламные, аналитические и рекомендательные скрипты стоит загружать отложенно, а основной код разделить на небольшие чанки. Это снизит Scripting и уменьшит Total Blocking Time, благодаря чему интерфейс быстрее станет отзывчивым.

Третье направление — работа с CSS и шрифтами. Critical CSS для первого экрана можно встроить в HTML, а остальную таблицу стилей загрузить позже. Для шрифтов нужно использовать `font-display: swap`, preload только для ключевого начертания и ограничить количество вариантов. Чтобы улучшить CLS, необходимо заранее резервировать место под изображения, рекламу и embeds через `width`, `height`, `aspect-ratio` и фиксированные контейнеры.

## 4. Реализация оптимизации

В репозитории добавлен файл `optimized-demo.html`, который демонстрирует одну практическую оптимизацию:

- LCP-изображение предзагружается через `rel="preload"`.
- Для главного изображения указан `fetchpriority="high"`.
- Для изображений заданы `width` и `height`, что уменьшает риск CLS.
- Некритичное изображение использует `loading="lazy"`.
- Второстепенный JavaScript подключён через `defer`.
- Critical CSS встроен в документ, поэтому первый экран не ждёт отдельный CSS-файл.

### Ожидаемый эффект повторного аудита

| Метрика | До оптимизации | После оптимизации, ожидаемо |
|---|---:|---:|
| LCP | около 4,2 с | 2,5–3,0 с |
| CLS | около 0,14 | до 0,05–0,08 |
| TBT | около 520 мс | 250–350 мс при дополнительной оптимизации JS |
| Performance Score | около 45–55 | 65–80 при комплексном внедрении |
